# Component Architecture

## Principles
- Build around repeated product patterns, not arbitrary visual fragments.
- Keep component APIs small and explicit.
- Separate content, state, and presentation where appropriate.
- Reuse tokens and variants.
- Avoid premature abstraction and giant all-purpose components.

## Component contract
For each reusable component document:
- Purpose
- Anatomy
- Variants
- Sizes
- States
- Responsive behavior
- Accessibility semantics
- Content constraints
- Examples and anti-patterns

## Common families
Navigation, buttons, links, fields, selection controls, dialogs, menus, tabs, cards, tables, alerts, badges, tooltips, empty states, skeletons, charts, and pagination.

Do not add a component solely because it appears in a design-system checklist.
